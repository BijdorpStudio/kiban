# #98 spike: should `Iban` become a `@JvmInline value class`?

This is the evaluation #98 asked for: decide whether `Iban` — a class whose only stored state is
one validated `String` — should become `@JvmInline value class Iban(val value: String)` before the
1.0 API freeze.

**Recommendation: no. Keep `Iban` a regular `class`.** The conversion works on the Kotlin side —
it compiles for every target, every existing test passes unchanged, and the private-constructor
invariant survives — but it costs three things kiban cannot give up:

1. **It deletes `Iban` from the Objective-C framework.** The generated header for the real
   `Kiban.xcframework` contains no `KibanIban` at all; `toIban`/`toIbanOrNull` return an untyped
   `id` (`Any?` in Swift). `samples/swift-console` no longer compiles. This is the question the
   issue was written to answer, and the answer is the opposite of what it expected: #9's `Result`
   erasure was *not* only a generics problem.
2. **It removes `Iban` from the Java-facing API too.** Every member is name-mangled with a `-`,
   which is not a legal Java identifier, and `toIban`/`toIbanOrNull` start returning
   `java.lang.String`. A Java caller that compiles against kiban today stops compiling, with no
   workaround available to them.
3. **The allocation it saves is not free — it deletes two caches.** `isSEPA` and
   `isInSwiftRegistry` are computed once in `init` today and stored; `pretty` is `by lazy`. A value
   class has no room for either, so both become recomputed-per-access. Measured: parsing gets ~19%
   faster, but property-heavy use gets **3.4× slower**.

Everything below was measured against this repo's actual toolchain (Kotlin 2.4.10, Gradle 9.6.1,
JDK 17 toolchain) by really converting `Iban` and building it — locally for the JVM, and on a
`macos-latest` GitHub Actions runner (Xcode 26.6, Swift 6.3.3) for the Apple targets, driven by
`.github/workflows/ios-interop-verify.yml` exactly as #98 proposed. The spike commits are on this
branch and are reverted by the commit that adds this document, so every shape quoted here can be
regenerated by re-running that workflow against them.

Two mechanical notes on how the spike was run, in case someone repeats it:

- Per [`CLAUDE.md`](../CLAUDE.md) this sandbox cannot resolve AGP or download the Kotlin/Native
  distribution, so the local JVM measurements used the documented Android-target-removal
  workaround. Nothing Apple-side was measured locally — all of section 4 comes from the macOS
  runner.
- `ios-interop-verify.yml` runs `apiCheck` before assembling the XCFramework, so the spike also had
  to carry refreshed API dumps; otherwise the job aborts before the header dump. The JVM dump came
  from `./gradlew jvmApiDump` locally and matched CI's own `jvmApiCheck` diff exactly; the klib dump
  was a one-word edit, taken verbatim from CI's `klibApiCheck` output.

## What the spike changed

`@JvmInline value class Iban private constructor(internal val value: String) : Comparable<Iban>`,
with the consequences the compiler forces:

- `isInSwiftRegistry` and `isSEPA` lose their backing fields and become computed getters (a value
  class has exactly one stored property).
- `pretty` loses `by lazy` for the same reason and re-derives the formatted string per access.
- the hand-written `equals`/`hashCode` go away — a value class generates equivalent ones over the
  underlying `String`.

Everything else — `compose`, `invoke`, `validate`, `ofValidated`, the `String` extensions,
`compareTo`, `toString` — was left untouched and needed no changes.

## 1. Does it compile, and do the invariants hold? Yes to both

The two Kotlin-side questions the issue raised both answer cleanly in favour of the change:

- **A private primary constructor is allowed on a value class**, so the "instances can only be
  obtained through validated factories" invariant survives verbatim. `Iban.ofValidated` and
  `Iban.invoke` keep working; no caller gains a way to build an unvalidated `Iban` *from Kotlin*.
- **The underlying property may stay `internal`**, so `value` doesn't have to be promoted to
  public API to satisfy the value-class rules.
- `Comparable<Iban>`, `@Throws`, the companion, and the top-level extensions all survive.

`./gradlew jvmTest` passes with **no test changes at all** — the full JVM suite (78 test cases
across six classes) is green on both shapes. The macOS runner compiled and linked `iosSimulatorArm64`,
`macosArm64`, `tvosSimulatorArm64` and `watchosSimulatorArm64` from the value-class source without
complaint, so Kotlin/Native's compiler is equally happy with it.

So this is not a "does it work" question. It works. It is a "what does it cost the published API"
question.

Kotlin callers don't notice any of this — the compiler re-inflates the types from metadata. Java
callers lose the type entirely, and this was verified rather than reasoned about. The same
four-line Java program, compiled with `javac` against the real compiled classes:

``` java
Iban iban = IbanKt.toIban("NL91ABNA0417164300");
System.out.println(iban.getPretty());
```

- against today's `class Iban`: compiles.
- against the value-class build:
  ```
  error: incompatible types: String cannot be converted to Iban
          Iban iban = IbanKt.toIban("NL91ABNA0417164300");
  error: cannot find symbol
          System.out.println(iban.getPretty());
    symbol:   method getPretty()
  ```

And there is no Java-side workaround, because `javap` shows every replacement member carries a `-`
in its name — `getPretty-impl`, `compareTo--SnQPyU`, `box-impl` — and `-` cannot appear in a Java
identifier. Java can neither call the accessors nor obtain a boxed `Iban` to call them on. The only
members left reachable from Java are the unmangled `equals`/`hashCode`/`toString` and the
`Comparable` bridge on the box — none of which can tell you anything about the IBAN.

This matters more for kiban than it would for most libraries. The README describes kiban as "a
continuation and re-implementation of the original `java-iban` library", `MIGRATION.md` is written
for people arriving from it, and `jvmMain` ships `typealias IBAN = Iban` specifically for them.
Turning the central type into something Java cannot name is the opposite direction.

The klib ABI, by contrast, barely moves. `klibApiCheck` on the macOS runner reports a **one-word**
difference for every non-JVM target:

```diff
-final class nl.bijdorpstudio.kiban/Iban : kotlin/Comparable<nl.bijdorpstudio.kiban/Iban>
+final value class nl.bijdorpstudio.kiban/Iban : kotlin/Comparable<nl.bijdorpstudio.kiban/Iban>
```

Every member keeps its name and signature there — the mangling is a JVM-backend artifact, not a
Kotlin-level one. So whatever else is wrong with this change, it is not a problem for
Kotlin-to-Kotlin consumers on Native, JS or Wasm.

It is also, unavoidably, a binary-incompatible change for existing Kotlin consumers: every
signature above is a different method, so anything compiled against 0.5.x breaks at runtime until
recompiled. That is survivable pre-1.0 on its own — it just isn't worth paying for on top of the
Java loss.

## 3. Performance: it trades an allocation for two lost caches

The motivation was avoiding one wrapper allocation per parsed IBAN. That part is real, but
`Iban`'s current shape isn't only a wrapper — it is also a small cache, and a value class cannot
keep it. Measured on the JVM with a throwaway benchmark (200 000 parses per sample over eight real
IBANs, 3 warmup rounds, median of 9 samples, deleted before committing). Crude wall-clock timing,
not JMH — treat the direction as sound and the exact ratios as approximate:

| Workload (200k iterations) | `class` (today) | `value class` | Effect |
| --- | ---: | ---: | ---: |
| parse only, read `plain` | 187 ms | 152 ms | **~19% faster** |
| parse + read `isSEPA`, `isInSwiftRegistry`, `pretty` once | 240 ms | 222 ms | ~7% faster |
| parse + read those three 10× per instance | 235 ms | **810 ms** | **~3.4× slower** |

The pattern is exactly what the source predicts: a value class wins where an `Iban` is parsed and
thrown away, and loses badly where one is held and asked questions, because every `isSEPA` read
becomes a fresh country-code lookup and every `pretty` read rebuilds the formatted string. The
third row is the shape most application code has — parse once at a boundary, then format and
inspect repeatedly.

Recovering the caches is not an option: storing them is precisely what a value class forbids.

## 4. Objective-C interop: `Iban` disappears from the framework entirely

This is the question #98 was actually written to answer, and it was run the way the issue asked —
`.github/workflows/ios-interop-verify.yml` on a `macos-latest` runner (Xcode 26.6, Apple Swift
6.3.3, Kotlin 2.4.10), against the converted source. `apiCheck` and the `iosSimulatorArm64` /
`macosArm64` / `tvosSimulatorArm64` / `watchosSimulatorArm64` test tasks all passed, and the real
`Kiban.xcframework` was assembled and its generated header dumped.

**There is no `KibanIban` in the generated header.** Not an empty class, not a renamed one — the
type is simply absent. The complete list of kiban interfaces the framework exports becomes:

```
@interface KibanCountryCodes : KibanBase
@interface KibanIbanParseException : KibanKotlinIllegalArgumentException
@interface KibanIbanParseExceptionMalformed : KibanIbanParseException
@interface KibanIbanParseExceptionMalformedKind : KibanKotlinEnum<...>
@interface KibanIbanParseExceptionUnknownCountryCode : KibanIbanParseException
@interface KibanIbanParseExceptionWrongChecksum : KibanIbanParseException
@interface KibanIbanParseExceptionWrongLength : KibanIbanParseException
@interface KibanModulo97 : KibanBase
@interface KibanIbanKt : KibanBase
```

`Iban` and `Iban.Companion` are gone, and the parse entry points that used to hand back a
`KibanIban *` now hand back an untyped `id`:

```objc
+ (id _Nullable)toIban:(NSString *)receiver error:(NSError * _Nullable * _Nullable)error
    __attribute__((swift_name("toIban(_:)")));
+ (id _Nullable)toIbanOrNull:(NSString *)receiver
    __attribute__((swift_name("toIbanOrNull(_:)")));
```

That is the *same* erasure #9 documented for `Result<Iban>` — `Any?` with no members — except it
now applies to every way of obtaining an IBAN, and it is worse in one respect: `Result`'s payload
could at least be recovered with `result as? Iban`, because `Iban` existed as a Swift type. Here
there is no `Iban` type in the framework to cast to at all. (Whether the opaque value can be
downcast to `String` — the underlying representation — was not tested; even if it can, every one
of `plain`, `pretty`, `isSEPA`, `isInSwiftRegistry`, `bankIdentifier`, `branchIdentifier`,
`countryCode`, `checkDigits` and `compareTo` is unreachable through it.)

The consequence isn't theoretical. `samples/swift-console`, which compiles and runs green on
`main` in this same workflow, fails to build against the value-class framework, with one error per
member access:

```
main.swift:10:22: error: value of type 'Any' has no member 'plain'
main.swift:30:26: error: value of type 'Any' has no member 'description'
main.swift:39:18: error: cannot convert value of type 'Any' to expected argument type
                         'any (~Copyable & ~Escapable).Type'
main.swift:47:27: error: value of type 'Any' has no member 'isSEPA'
main.swift:48:38: error: value of type 'Any' has no member 'isInSwiftRegistry'
main.swift:57:50: error: value of type 'Any' has no member 'bankIdentifier'
main.swift:58:52: error: value of type 'Any' has no member 'branchIdentifier'
```

So the hypothesis #98 was built on — that #9's `Result` erasure was specific to generics and
wouldn't apply to a non-generic value class like `Iban` — is **wrong**, and now measured rather
than assumed. Generic erasure and value-class erasure are two different gaps that happen to produce
the same `Any?`. The issue's other counter-evidence — that Kotlin's built-in value classes such as
`UInt` came through cleanly in #9 — doesn't generalize either: that observation was about Swift
Export, and those types are mapped to native Swift/Objective-C types by the compiler itself. A
user-defined value class gets no such treatment on the Objective-C path.

Swift Export was not re-tested here. #9 established that it can't reach kiban's published-artifact
consumers at all (it requires direct Gradle-project integration) and that it crashed mid-experiment
on this toolchain, so a better Swift Export result would not change the recommendation while the
Objective-C path remains the one kiban's consumers actually get.

## 5. Considered alternative: `expect`/`actual` with a value class on some targets only

An obvious follow-up idea: keep the regular class where the erasure bites (JVM for Java, the Apple
targets for Objective-C) and make `Iban` a value class only on the remaining targets, via
`expect class Iban` in `commonMain` with per-platform actuals.

**The compiler rejects this outright.** Probed on this toolchain with a minimal
`expect class Probe98` actualized as a regular class on `jvm` and as a `value class` on `js`:

```
e: Probe98.js.kt:3:20 The 'expect' and the 'actual' declarations are incompatible.
  expect: public final expect class Probe98 : Any
  actual: public final actual value class Probe98 : Any
```

The `value` modifier is part of the expect/actual matching contract, like `enum` or `fun`: every
actual must have the same class shape as the expect. It cuts both ways — `expect value class`
would force *every* actual to be a value class, including the JVM and Apple ones that can't afford
it — and an `actual typealias` goes through the same checker, so there is no back door.

Even if the language allowed it, the split would not pay for itself:

- The targets that must keep the regular class are the ones with actual consumers. Ruling out JVM
  and the seven Apple targets leaves the value class only on `linuxX64`/`linuxArm64`/`mingwX64`/
  `js`/`wasmJs`.
- The win shrinks further there: `Iban : Comparable<Iban>` means any use through the interface, in
  a nullable position, or as a generic argument boxes anyway, on every backend — and the ~3.4×
  property-read regression from section 3 would ship on exactly those platforms.
- The cost is structural: expect/actual *classes* are still Beta (the probe also emitted the
  `-Xexpect-actual-classes` warning, and JetBrains discourages them in published libraries), and
  `Iban`'s entire body plus its companion would need duplicating into every actual or hollowing
  out into shared internal functions, taking on per-platform semantic drift (identity vs. inlined
  equality) in the library's central type.

## Verdict

Don't do it. `Iban` stays a regular class, and #98 can close as answered.

The Kotlin ergonomics are unchanged and the JVM allocation win is real, but it is small, it comes
bundled with a much larger regression for the property-reading case, and it is paid for by
deleting kiban's central type from both non-Kotlin consumption paths at once — Swift/Objective-C
and Java. A library whose whole point is to be usable from every platform Kotlin reaches cannot
adopt a representation that only Kotlin callers can see.

Two things would have to change before this is worth revisiting, and neither is on kiban's side:

- Kotlin/Native's Objective-C exporter would need to export user-defined value classes as real
  types (or Swift Export would need to both stabilize *and* gain published-binary support, per #9).
- The stored-vs-computed regression would still need answering — that one is kiban's own and could
  be mitigated by not caching `isSEPA`/`isInSwiftRegistry`/`pretty` in the first place, at a cost
  the numbers above quantify.

Until then the `class` shape is the one that keeps the type visible to every consumer.
