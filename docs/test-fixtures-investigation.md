# #67 spike: where do test helpers like `Iban.random()` live?

This is the write-up #67 asked for: pick one of the three shapes for hosting consumer-facing
test helpers — most concretely a per-country `Iban.random()` — that shouldn't ship in the main
artifact.

**Recommendation: shape 2, a separate `kiban-test` Kotlin Multiplatform module**, published as
`nl.bijdorpstudio.kiban:kiban-test`. Gradle's `java-test-fixtures` does compose with the
Kotlin Multiplatform plugin on this repo's toolchain, but only for the JVM target, and — the
decisive part — its fixtures variants are **not** included in the published module metadata, so
`testFixtures("nl.bijdorpstudio.kiban:kiban")` cannot resolve for an external consumer at all.

Everything below was measured against this repo's actual toolchain (Kotlin 2.4.10, Gradle
9.6.1, JDK 17 toolchain) with throwaway probe modules, not inferred from documentation. The
probes were deleted before committing; the observations they produced are quoted verbatim.

## How the probe was set up

Two scratch modules in this build:

- `:probe` — `kotlin("multiplatform")` with `jvm()` and `linuxX64()` targets, plus
  `` `java-test-fixtures` `` and `` `maven-publish` ``. `commonMain` declares a public `Probe`
  and an `internal InternalProbe`.
- `:probe-consumer` — a second KMP module consuming `:probe`'s fixtures.

Note that per [`CLAUDE.md`](../CLAUDE.md) this sandbox cannot resolve AGP (`dl.google.com`
blocked) or download the Kotlin/Native distribution (`download.jetbrains.com` blocked), so the
probe used the documented Android-target-removal workaround and could not *compile* the
`linuxX64` target. That does not affect any finding below: the questions this spike had to
answer are about source-set/compilation *creation*, dependency *resolution* and published
*metadata*, all of which Gradle answers at configuration time without a Kotlin/Native compiler.

## 1. Does KMP support test fixtures at all?

**Partially — JVM target only, and not in a publishable form.** This is shape 3 in the issue's
framing, not shape 1.

Applying `` `java-test-fixtures` `` to a KMP module does *not* fail, which is a change from the
"does not compose at all" expectation the issue was written under. It registers a real Kotlin
compilation:

```
SOURCE_SETS:   [commonMain, commonTest, jvmMain, jvmTest, jvmTestFixtures, linuxMain,
                linuxTest, linuxX64Main, linuxX64Test, nativeMain, nativeTest]
COMPILATIONS:  {jvm=[main, test, testFixtures], linuxX64=[main, test], metadata=[commonMain, main]}
```

Three things to read out of that:

- There is a `jvmTestFixtures` source set and a `testFixtures` compilation **on the `jvm`
  target only**. `linuxX64` gets `[main, test]` and nothing else.
- There is no `commonTestFixtures` source set, so there is nowhere to put a helper that all
  targets share. Fixtures written here are JVM-only by construction, not JVM-only by accident.
- `compileTestFixturesKotlinJvm` and `testFixturesJar` are real tasks and do work. Kotlin code
  in `src/jvmTestFixtures/kotlin` compiles against `commonMain`, and the association with the
  main compilation is set up correctly — a fixture referencing `internal InternalProbe`
  compiled without error, producing
  `probe/build/classes/kotlin/jvm/testFixtures/ProbeFixtures.class`. So the long-standing
  friend-path complaint (KT-34901) does not apply to this path.

### The blocker: fixtures don't reach the published metadata

`testFixturesApiElements` and `testFixturesRuntimeElements` exist as outgoing variants of the
project:

```
Variant jvmApiElements
Variant jvmRuntimeElements
Variant jvmSourcesElements
Variant testFixturesApiElements
Variant testFixturesRuntimeElements
```

but neither publication generated by the KMP plugin contains them:

```
probe/build/publications/jvm/module.json
  -> [jvmApiElements-published, jvmRuntimeElements-published, jvmSourcesElements-published]
probe/build/publications/kotlinMultiplatform/module.json
  -> [metadataApiElements, metadataSourcesElements,
      jvmApiElements-published, jvmRuntimeElements-published, jvmSourcesElements-published,
      linuxX64ApiElements-published, linuxX64SourcesElements-published]
```

The fixtures variants belong to Gradle's `java` component, which the KMP plugin does not
publish; the `testFixturesJar` is never attached to either publication. A consumer writing
`testImplementation(testFixtures("nl.bijdorpstudio.kiban:kiban:0.6.0"))` would get a resolution
failure, not a JVM-only helper set. That is the finding that rules shape 1 out — not the
multiplatform gap on its own.

### It does work for in-repo project dependencies

For completeness, the same fixtures *are* consumable inside this build, which is the one thing
`java-test-fixtures` would still buy us:

```kotlin
jvmTest.dependencies {
    implementation(project.dependencies.testFixtures(project(":probe")))
}
```

`:probe-consumer:jvmTest` passed against a fixture-provided value. Two caveats worth recording:
the KMP source-set DSL has no `testFixtures(...)` accessor, so it has to be spelled
`project.dependencies.testFixtures(...)`; and moving the same dependency to `commonTest`
resolves to nothing for the native target — `linuxX64CompileKlibraries` came back empty
(`RESOLVED: []`) with the fixtures dependency declared, exactly as the missing compilation
predicts.

## 2. Separate module

**This is the answer.** A `kiban-test` KMP module in this repo, mirroring `:library`'s full
target list, depending on `:library`, published as `nl.bijdorpstudio.kiban:kiban-test`.

It is the only shape that gives every one of kiban's 19 targets the same helper, and the only
shape that survives publication. Its costs are real but bounded and already understood:

- A second published artifact and its own API dump. See question 4.
- Build-file duplication of `:library`'s publish/POM/target-list ceremony — which is why #85
  scopes a shared convention plugin as part of adding the module, rather than copy-pasting it.
- Consumers depend on it by coordinate (`testImplementation("nl.bijdorpstudio.kiban:kiban-test:…")`)
  rather than by capability. Declaring the dependency on `:library` as `api` makes that a single
  line for the consumer — they get `Iban` and friends transitively, which is what
  `testFixtures(...)` would have given them automatically.

There is no lighter option that actually publishes. The spike checked for one and did not find
it.

## 3. JVM/Android-only fixtures — acceptable?

**No.** The issue anticipated this and the answer holds: kiban declares 19 targets, and its
whole value proposition is that the same IBAN code runs on all of them. A helper that a
consumer can call from `jvmTest` but not from `commonTest` or `iosSimulatorArm64Test` fails the
exact audience it exists for — and, worse, would push consumers to duplicate the generator in
their own common source set, which is the outcome the helper is meant to prevent.

Not verified here: whether AGP 9.3.1's `androidLibrary { … }` (this repo uses the
`com.android.kotlin.multiplatform.library` plugin, not `com.android.library`) exposes its own
`testFixtures` support on top of the KMP model, and whether that one publishes. It is moot for
the decision — Android plus JVM is still not 19 targets — but it is the one sub-question this
sandbox could not answer, since AGP cannot be resolved here at all.

## 4. API-dump implications

`kiban-test` should be validated by `binary-compatibility-validator` like `:library` is. The
root `apiValidation` block already validates every subproject that isn't explicitly ignored
(`ignoredProjects` currently holds only `jvm-cli`), so a new module is covered by default —
adding it means committing a real `kiban-test/api/` dump, not configuring anything.

Two things to decide as it lands rather than now:

- The first dump has to be generated on a host with the full target matrix (Android plus
  Kotlin/Native), which this sandbox is not. #85's verification section already carries that
  requirement.
- Test-helper API is allowed to move faster than the core. The dump is there to make a break
  *visible and deliberate* at review time, not to freeze `kiban-test` to the same 1.0
  compatibility promise `:library` will take on. Worth stating that explicitly in the module's
  own README section when it exists, so a future breaking change to `Iban.random()` isn't
  argued about as if it were a core ABI break.
